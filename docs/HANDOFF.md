## 1. いまどこまで進んでいるか

**遊びとして一周する状態になっていて、本番でも動いている。**

| 段階 | 中身 | 状態 |
|---|---|---|
| 1 | DB定義一式（[schema.sql](./schema.sql)）とカード92枚 | ✅ |
| 2 | クエスト一周（カードをめくる→着いた→お題→できた／ここまで） | ✅ |
| 3 | ~~歩いた距離と軌跡の記録・地図のマス~~ | ❌ **取り外した（§1.4）** |
| 4 | PWA（ホーム画面に追加）・Vercelへデプロイ | ✅ https://arquest-app.vercel.app |
| 5 | 日記（写真＋ひとこと・詳細・編集・削除） | ✅ |
| 6 | 時間帯通知（pg_cron + Web Push） | ⬜ **次はここ** |

ごほうびはEXPだけになった（できた20／まだ10の固定）。距離による加算は無い。

### 動いている画面

```
/            ホーム → 移動カード（めくる）→ 移動中 → 行動カード（めくる）→ 達成
/diary       日記帳（一覧）
/diary/<id>  日記の詳細（編集・削除）
```

### まだ無い画面（下のタブに薄く出してある）

相棒・マップ・設定・稼働時間設定・ログイン（匿名のみ）。

**マップ（地図塗り）は無くなった。** 塗る材料（`visited_cells`）が位置情報と一緒に消えたため。
タブからも外すか、別の中身にするかは決めていない。

### 位置情報について

**このアプリは位置情報を一切使わない。** `navigator.geolocation` を呼ぶコードは
リポジトリに1行も無い。地図・スポット検索・経路・軌跡・距離、すべて取り外してある。

もともと移動カードは座標に紐付かず、到着もGPSではなく利用者の自己申告なので、
**遊びの成立に位置情報は要らない**（仕様書§2.2）。詳しくは §1.4。

## 1.4 位置情報をやめた経緯（2026-08-22）

**実機で5時間GPSが回り続け、利用者の私物の携帯の電池を使い切った。**

原因はコードの構造にあった。

1. クエストの状態はデータベースに残る（`status` が `moving` / `acting`）
2. `useQuestTrail` は `acting` を見た瞬間、**利用者の操作なしに** `start()` を呼んでいた
3. `enableHighAccuracy: true` / `maximumAge: 0` で最も電気を食う設定
4. **止まる条件が「`acting` でなくなること」しか無かった。**
   `visibilitychange` も `pagehide` も時間の上限も無く、画面を消しても止まらない
5. 「一度止めて再起動する」という最も自然な対処も効かない。
   データベースの `acting` が消えていないので、開いた瞬間にまた始まる

コードのコメントには「『ついた』ボタンを押した直後に始まるので、許可を求める画面が
利用者の操作の直後に出る」と書いてあった。**復帰したときには成り立たない説明**で、
安全である理由をコメントに書きながら、コードはそうなっていなかった。

**開いただけで測位が始まり、利用者に止める手段が無い**という作りは、
歩いた距離の記録と引き換えにしてよいものではないと判断して、機能ごと取り外した。

> 電池の膨張自体は数週間から数年かけて進む現象なので、この一件が原因ではない。
> ただし**壊れかけの電池に重い負荷をかけて表面化させた**のは確かで、
> 「アプリが端末の資源を握りっぱなしにする」ことの実害はここに出た。

**この判断はポートフォリオの中身として残す価値がある**（§9）。
機能を増やした話より、**自分で見つけて、その日のうちに落とした**話のほうが強い。

## 1.6 見た目の決まりごと（2026-08-26 時点）

**モックアップは [画面イメージ.png](../画面イメージ.png)（リポジトリ直下）が最新。**
いまの画面はこれに準拠している。`screen-images/` の12枚は緑基調だった1世代前、
`screen-shot/` はさらに古い（リポジトリには入れていない）。

- **配色は紺地にゴールド。** 面は明るさで3段に分ける
  （`--navy` 画面の地 → `--navy-panel` カード → `--navy-tile` タイル）。
  枠線を増やさずに面の重なりが読める
- **文字色が2系統ある。** 地が紺の場所と、白いカードの上とで読める色が逆になる。
  `--ink`（明るい）と `--ink-card`（暗い）。白い面は**主役カードと下のタブだけ**
- **ゴールドも2つある。** `--gold` は紺の上で光るが、白いカードの上では薄すぎる。
  白い面に置くぶんは `--gold-ink`（暗いゴールド）を使う
- **進むボタンの文字は白ではなく紺。** ゴールドが明るいので、白文字だと日なたで読めない
- **画面で唯一の白い面が「めくったカード」。** ここだけ明るいので目が迷わない
- よく使う形は [globals.css](../src/app/globals.css) に名前を付けてある
  （`aq-card` `aq-hero` `aq-btn` `aq-btn-quiet` `aq-window` `aq-tile` `aq-label`）。
  画面ごとに書き写すとズレていくので、変えるときはここ1か所
- **カードは「めくる」。** 裏はゆっくり揺れて押せると伝え、表は横長にする
  （縦長だと幅が狭く、一文がすぐ折り返して読みにくい）
- **押せるものは必ず48px以上。** 文字だけのボタンはアプリ内に無い
- 相棒は右向きの絵（`normal.png`）なので、吹き出しの**左**に置く
- **相棒の動きは絵1枚で作る。** 潰れも伸びもCSSの変形。
  以前は着地だけ `squashed.png` に差し替えていたが、2枚は縦横の比率が違う
  （1.28:1 と 1.89:1）ため、入れ替わった瞬間が見えて違和感が出た

### 色を変えるときは必ずコントラストを測る

紺地は明るい文字、白いカードは暗い文字と**逆転する場所がある**ので、
目分量だと必ずどこかが読めなくなる。13組を測ってあり、すべてAA基準（4.5以上）を満たす。
特に注意が要るのは11pxの小さい文字（カード内のラベル・下のタブ）で、
モックアップに忠実な `#A97F1E` では 3.66 しかなく不足だった（いまは `#8D6916` で 5.04）。

## 1.5 確定版（2枚カード方式）で何が変わったか

### なぜ変わったか

直前まで「エリア抽選方式」（地図にエリアの円を出し、到着後に1回だけ抽選する）を正式仕様にしていたが、
**行き先が実質的に「座標」として決まってしまい、位置情報の役割が「エリアへの到達判定」の一点に
集中しすぎていた**ため不採用にした（仕様書§10）。

確定版は、移動カードの内容を**座標に一切紐付けない曖昧な指示**にすることで、
「行き先が本当にわからない」体験を保ちながら、位置情報の利用を
**「行動カードを引いた後」と「スポット検索を押した時」だけ**に絞り込んでいる。

## 2. 動く状態にするまで（新しいPCでの初回手順）

```bash
nvm use              # .nvmrc を読んで Node v24 に切り替わる
npm install
npm run dev          # http://localhost:3000
```

Node.js は **v24 系**。`.nvmrc` に `24` を記録してあるので、`nvm use` だけで揃う。

**バージョンを揃える理由。** 自宅PCが v22（npm 10）、訓練校が v24（npm 11）だったとき、
`npm install` のたびに `package-lock.json` に38行の差分（`libc` フィールド）が出続けた。
壊れはしないが、本当に意味のある変更がノイズに埋もれる。

**`.env.local` は git に載らないので、PCを移ったら手で作り直す。** 中身は §5-5 参照。

### 動作確認の手順

**位置情報を使わなくなったので、机の上で全部確かめられる。**
以前あった「DevToolsで緯度経度を偽装する」手順は不要になった。

ブラウザで `http://localhost:3000` を開き、
クエストを受注 → カードをめくる → 出発する → 着いた → お題をめくる → できた、
と押していけば一周する。日記まで書ければ全機能を通ったことになる。

**写真つきで日記を保存したら、GPSが消えているかを実物で確認する。**

```bash
node scripts/check-exif.mjs --list
node scripts/check-exif.mjs --storage <場所>
```

## 4. 技術的な判断と、その根拠（実測にもとづく）

ポートフォリオのREADMEや面接で説明できるよう、根拠つきで残す。
**ここは仕様が変わっても消えない。**実測で分かった事実の記録だからである。

> ### 📌 4-1 〜 4-9 は、いまアプリに無い機能の話
>
> 2026-08-22 に位置情報を全部やめた（§1.4）ので、
> **4-1〜4-9 が対象にしているコードは、もうリポジトリに無い。**
> リンク先のファイルも消えている（`git log` から辿れる）。
>
> それでも消さずに残しているのは、ここが**実測して判断した記録**だからである。
> 「公開デモサーバーが profile 指定を無視していた」「キャッシュが静かに壊れていた」
> といった事実は、機能を消しても無くならない。
> 面接で話せるのは動いている機能の一覧ではなく、こちらのほうである。
>
> **いまも生きているのは 4-10 と 4-11。** 4-11 が今回いちばん重い。

### 4-1. 経路サービスを OSRM → Valhalla に変更した

**公開デモサーバー（router.project-osrm.org）は profile 指定を無視し、自動車の経路しか返さない**。
`foot` / `walking` / `driving` の3つで距離・時間・経路が完全に一致することを確認した。

自動車の経路は一方通行・進入禁止・歩行者専用道の制約を受けるため遠回りになる。
実測（阪神尼崎→出屋敷）:

| | 距離 |
|---|---|
| 直線距離 | 1.17 km |
| **徒歩ルート（Valhalla）** | **1.34 km** |
| OSRMデモ（実質は自動車） | 1.60 km |
| 自動車ルート（Valhalla） | 1.89 km |

→ FOSSGISが公開する **Valhalla**（`costing: "pedestrian"` が正しく機能）に変更。
OSRMはValhalla停止時の代替として残し、どちらを使ったかを `profile` で返している。
自動車で代替した場合は画面に注意書きが出る。

Valhallaは経路を **encoded polyline（精度6）** で返すため、デコード処理を自前で実装した
（`lib/routing.ts`（削除済み））。一般的な精度5と間違えると座標が10分の1になる。

> **⚠ 確定版§5は「徒歩ルート計算＝OSRM」と書いてある。** 上の実測と矛盾するので、
> **仕様書側を直すか、コードをOSRMに戻すかの判断が要る**（§8-1）。
> なお確定版で寄り道ルート（§2.4③）が採用されたことにより、**この実装は本編で使われる**ようになった。

### 4-2. Overpass API は User-Agent が必須

名乗らずにリクエストすると、`overpass-api.de` は **406**、`kumi.systems` は **429 +
「Please include a meaningful User-Agent string」** で拒否される。
OSMの利用規約でアプリの名乗りが求められているため。

また `overpass.osm.ch` は**スイス周辺のデータしか持たない地域限定サーバー**で、
日本の座標では **HTTP 200 で 0件** を返す。エラーにならないので気づきにくい。使わないこと。

Overpassはタイムアウト時にも **HTTP 200 で `remark` だけ返す**ことがあるため、
`remark` があれば失敗として扱っている。

回数制限も実際に食らった（429）。**キャッシュを必須とする判断は、この実測で裏付けられた。**
確定版§2.4の「更新は時間ではなく距離（200m移動ごと）」も、同じ理由から来ている。

### 4-3. MapLibre v6 のワーカーがバンドル後に見つからない

MapLibreはタイルの取得・解析を Web Worker に任せているが、v6 は
`import.meta.url` を基準にワーカーのファイルを探しに行く。
Next.jsがコードをまとめ直すと、その場所にファイルが存在しない。

結果、**ワーカーが起動せず、タイルが永久に読み込まれず、エラーも出ないまま
「地図を読み込み中…」で固まる**。マーカーはHTML要素なので表示され、
「ピンは出るが地図が出ない」という紛らわしい状態になる。

対処: `scripts/copy-maplibre-worker.mjs` で `maplibre-gl-worker.mjs` と
`maplibre-gl-shared.mjs` を `public/maplibre/` にコピーし、`setWorkerUrl()` で場所を明示。
`postinstall` に登録してあるので `npm install` のたびに自動でコピーされる。
**2ファイルセットで必要**（ワーカー本体が同じフォルダの shared を読むため）。

> **⚠ 確定版§5は「地図描画＝Leaflet」と書いてある。** 現状の実装はMapLibreで、
> この知見もMapLibre前提である（§8-1）。

### 4-4. GPSの点は間引かないと距離が水増しされる

`watchPosition` は静止していても1〜2秒ごとに位置を知らせ、GPS誤差で座標は常に揺れる。
全部足すと「座っているだけで距離が増える」。`hooks/useWalkTrail.ts`（削除済み） で2種類を捨てている。

| 条件 | 閾値 | 理由 |
|---|---|---|
| 精度が粗い点 | ±50mより粗い | この精度の点で距離を足すと、歩いていない分まで記録に乗る |
| 動いていない点 | 前回から10m未満 | GPS誤差の揺れは数メートル。歩行なら10mは10秒足らずで進む |

**±50mの根拠が変わった。** 旧仕様では「到達判定の半径100mの半分」を根拠にしていたが、
確定版に到達判定は無い。いまの根拠は**記録された距離が実際に歩いた距離とずれないこと**だけなので、
**歩いてみて数字が合わなければ調整してよい**（もう連動する相手がいない）。

**開発中（`npm run dev`）は精度の基準を±1000mに緩めている。** 開発ツールの偽装位置は
精度が粗い固定値で返るため、本番と同じ基準だとテスト用の位置が全部捨てられて動作確認できない。
本番ビルドでは±50mに戻る（`process.env.NODE_ENV` で自動切替）。

### 4-5. 位置情報のエラーは種類で扱いを分ける

`watchPosition` は1回失敗しても見張りは続く仕様。どんなエラーでも `clearWatch` すると、
トンネル・地下・ビル影で測位が途切れるたびに追従が止まってしまう。

| エラー | 扱い |
|---|---|
| code 1（許可されていない） | 追従を停止。設定を変えない限り絶対に成功しない |
| code 2（測位できない） | **追従を継続**。お知らせだけ出す |
| code 3（時間切れ） | **追従を継続**。お知らせだけ出す |

確定版では**電車・バスでの移動中は位置情報を使わない**ので、
地下・トンネルで測位が切れる場面そのものが減る。ただし行動カード後の軌跡記録では引き続き必要。

### 4-6. 同じコードでも、PCによって外部APIに繋がらないことがある

zip転送後、自宅PC（Windows/WSL）で `/api/pois` が **502で全滅**した。訓練校のMacでは動いていた。

切り分けると、**`curl` では成功するのにアプリ（Node）からだけ失敗**する。
さらに Valhalla・CARTO・GitHub には繋がり、**Overpassだけ**が落ちる。

原因は、ドメインが複数のIPを持つときの Node の接続方式にあった。
Nodeは全アドレスを少しずつずらして試し、**1つあたり250msで見切って次へ移る**。

| overpass-api.de の接続先 | 実測 | Nodeの制限 |
|---|---|---|
| 65.109.112.52 | 373ms | 250ms → 打ち切り |
| 162.55.144.139 | 315ms | 250ms → 打ち切り |

**あと少しで繋がるところで毎回打ち切られていた。** サーバーがドイツにあるので
往復300ms超は異常ではなく普通のこと。訓練校では回線が速く、たまたま間に合っていただけ。

Valhalla・CARTOが無事だったのは、IPアドレスが1組しかなく「次に移る先」が無かったため。
「一部のAPIだけ落ちる」という紛らわしい出方をしていた。

対処: `src/instrumentation.ts`（削除済み） で待ち時間を **250ms → 1000ms** に。
`instrumentation.ts` はNext.jsの決まりで、**サーバー起動時に1回だけ**走る（ファイルを作った後は再起動が要る）。

長くしすぎない理由は、IPv6が使えない環境（このWSLがそう）で
IPv4に切り替わるまでの待ちがそのまま伸びるため。実測最大373msに余裕を持たせて1秒にした。

### 4-7. キャッシュは「どの範囲を調べたか」を記録しないと静かに壊れる

`pois` にキャッシュするとき、素直に「半径内に1件でもあれば命中」と作ると壊れる。

```
1回目 尼崎駅で検索      → 30件を保存
2回目 800m東で検索      → 重なった部分の3件だけがヒット
                        → 「キャッシュにある」と誤判定してOverpassに行かない
                        → 東側の20件が永久に出てこない
```

**エラーが出ない。** 画面には3件だけ並び、利用者には「この辺には3つしかない」と見える。
しかも `pois` にデータが溜まるほど悪化する（どこで検索しても数件はヒットするようになるため）。

原因は、`pois` が「スポットの位置」しか知らず「どの範囲を調べ終わったか」を知らないこと。
そこで **`poi_searches`（中心・半径・検索日時）** を追加し、
「今回の円が過去の円に完全に収まるか」＝ `中心間の距離 + 今回の半径 ≦ 記録した半径` で判定する。

**ただしこれだけだと、今度はキャッシュがほぼ効かない。**
同じ半径800mで検索し続けると `1 + 800 > 800` となり、1mでも動けば必ず外れる。
実測でも100m・300m・800mすべて命中しなかった。歩いて使うアプリでは致命的。

対処: **Overpassには要求の2倍（1600m）で取りに行き、その範囲を記録する。**
返すのは要求どおり800m以内だけ。広く取るのは保存のためであって表示のためではない。

| | 時間 |
|---|---|
| 初回（Overpassへ） | 9.5秒 |
| 同じ地点で再検索 | 0.28秒（34倍速） |
| **500m移動して再検索** | **0.28秒（命中）** |

面積が4倍になるので1回の問い合わせは重くなるが、**問い合わせ回数そのものが激減する**。
Overpassは回数制限のある無料サーバーなので、この取引は有利。

**確定版§2.4の「200m移動ごとに更新」と噛み合う。** 歩きながら何度も呼ぶ機能になったため、
このキャッシュ設計は旧仕様のとき以上に効く。

### 4-8. 表示の上限を保存の上限に使うと、キャッシュが嘘をつく

§4-7 でキャッシュの範囲判定を直したが、**同じ壊れ方がもう1か所に残っていた。**

`lib/overpass.ts`（削除済み） は「地図が埋まらないように」近い順60件へ絞ってから返し、
`api/pois/route.ts`（削除済み） は**その60件だけを保存して「半径1600mを調べ済み」と記録**していた。
以後その円の中はキャッシュに命中し、**60件しか返らない状態が固定される。**

60件は**画面の上限**であって、保存の上限ではなかった。役割の違う2つに同じ数を使ったのが原因。

実測（半径1600m・名前つきのみ・スポットの種類を広げた後）:

| 場所 | Overpassが返せる件数 | 旧: 保存された件数 |
|---|---|---|
| 尼崎 | 180件でも足りない（喫茶店だけで55件） | 60件 |
| 梅田 | **600件でも足りない** | 60件 |

対処は3つ。

1. **絞る位置を変えた。** 保存は取れた全件、絞るのは画面に返す直前だけ（`DISPLAY_LIMIT`）
2. **Overpassへの要求を180→600件に上げた。** 1500件にすると混雑時にエラーページが返ったため600で止めた
3. **取り切れなかったときは `poi_searches` に記録しない。** 打ち切られた結果を「調べ済み」と
   記録すると、欠けたまま固定される。都市部で毎回Overpassに行くのは損だが、
   **静かに間違った結果を返し続けるよりよい**

**Overpassの打ち切りは距離順ではない**（`out center 600` は近い順に600件ではない）ため、
「取り切れなかったが近いものは揃っている」とも言えない。3の判断はここから来ている。

### 4-9. 位置情報のエラー案内はOSごとに変える

Macで開発したため「Macのシステム設定を確認してください」と決め打ちしていた。
Windowsにその画面は存在せず、実際に原因究明を妨げた（真因はWindowsの位置情報サービスがOFF）。

仕様書§2.1のとおり、このアプリはiPhone・AndroidにPWAとして入れて使う。
**利用者のOSはMacでないほうが普通**なので、`navigator.userAgent` を見て案内先を出し分けている。

位置情報は「ブラウザの許可」と「OS本体の許可」の二段階で、どちらが切れていても失敗する。
両方に触れる文面にしてある。

### 4-10. その他

- **`useEffect` の中で state を更新しない。** Next.js 16のESLintに止められる。
  「描画 → 効果 → state更新 → また描画」の連鎖が起きるため。
  出来事（イベント）が届いたその場で処理するほうが素直。
- **`scrollbar-gutter: stable`。** スクロールバーの有無で使える幅が変わり、
  中央寄せしているものが画面ごとに横へずれていた。
- **ポップアップやスポット名は `textContent` で組み立てる。** OSMの投稿データ（他人が書いた文字列）を
  HTML文字列として埋め込むとクロスサイトスクリプティングの余地が生まれる。
  この考え方は、外から来た文字列を扱う場所すべてに当てはまる。
- **繰り返す絵は「枠の幅 ÷ 絵の幅 + 1」枚並べる。** 移動中の景色が2枚では途切れた。
- **EXIFのGPSは文字列で探しても見つからない。** 項目は番号（`0x8825`）で入っている。

### 4-11. 端末の資源を使う処理は、開始条件より停止条件のほうが難しい

**実機で5時間GPSが回り続け、利用者の携帯の電池を使い切った**（§1.4）。
ここが今回いちばん高くついた失敗なので、教訓として残す。

書いたときに考えていたのは「**いつ始めるか**」だけだった。

```js
useEffect(() => {
  if (!acting) return;
  start();                    // ← 開始条件はよく考えてある
  return () => { stop(); };   // ← 停止は「acting でなくなったとき」だけ
}, [acting, ...]);
```

`acting` はデータベースから復帰する値なので、**アプリを開いただけで測位が始まる。**
そして止まる道が1本しか無い。画面を消しても、他のアプリに移っても、5時間経っても止まらない。

| 用意すべきだった停止条件 | 無かった |
|---|---|
| 画面が見えなくなったら止める（`visibilitychange`） | ❌ |
| ページが隠れる・凍るときに止める（`pagehide`） | ❌ |
| 一定時間まったく動きが無ければ止める | ❌ |
| 利用者が自分で止められる操作 | ❌ |

**「一度止めて再起動する」が効かなかったのが特に悪かった。**
利用者が取れる最も自然な対処が、状態がデータベースに残っているせいで無効になる。
自力で抜け出せない作りは、単に電池を食うより性質が悪い。

**コメントが嘘をついていたことも記録しておく。** その `useEffect` のすぐ上には
「『ついた』ボタンを押した直後に始まるので、許可を求める画面が操作の直後に出る」と書いてあった。
**書いた時点では本当だったが、復帰の経路では成り立たない。**
安全である理由をコメントに書くと、それ自体が検証済みのように見えてしまう。

一般化するとこうなる。

> 位置情報・カメラ・マイク・録音・常時通信のように**端末の資源を握る処理**は、
> 開始条件と同じ密度で、**停止条件・利用者が止める手段・上限時間**を設計する。
> とくに「状態を復帰させる」作りでは、
> **利用者の操作なしに動き出す経路が無いか**を必ず確かめる。


### 5-3. 作ったテーブル

```sql
-- スポットのキャッシュ（仕様書§6の pois）
create table if not exists pois (
  id bigint generated always as identity primary key,
  source_id text not null unique,        -- OSM上のID（例: "node/123456"）
  name text not null,
  category text not null,
  geom geography(Point, 4326) not null,  -- 地球が丸いことを考慮して距離計算できる型
  cached_at timestamptz not null default now()
);

create index if not exists pois_geom_idx on pois using gist (geom);
create index if not exists pois_cached_at_idx on pois (cached_at);

alter table pois enable row level security;
create policy "pois_select_all" on pois for select using (true);
grant all on table pois to service_role;

-- 「どの範囲を調べ終わったか」の記録（仕様書§6に無い。§4-7の理由で追加）
create table if not exists poi_searches (
  id bigint generated always as identity primary key,
  center geography(Point, 4326) not null,
  radius_m integer not null,
  searched_at timestamptz not null default now()
);

create index if not exists poi_searches_center_idx on poi_searches using gist (center);
create index if not exists poi_searches_searched_at_idx on poi_searches (searched_at);

alter table poi_searches enable row level security;
grant all on table poi_searches to service_role;
```

`source_id` の `unique` が重要。これがあるから `upsert` で重複が防げる。

`gist` は**位置情報専用の索引**。普通の索引は大小の並び順で探すので
「この円の中にあるか」という2次元の問いには使えない。

> **⚠ この2つ（`pois` / `poi_searches`）は、いまアプリから使われていない。**
> 位置情報をやめたときに、読み書きするコードだけを消した（§1.4）。
> **テーブルと過去のデータはそのまま残してある。**消すのは戻せないため。
>
> 同じ理由で `quest_trajectories`（軌跡）と `visited_cells`（塗ったマス）も残っているが、
> もう増えない。`users.total_distance_m` と `daily_activity_stats` も同様で、
> [profile.ts](../src/lib/profile.ts) はこれらを読まなくなった。
>
> 整理するなら、通知（段階6）まで進めて全体像が固まってからでよい。

### 5-4. 作った関数（RPC）

PostgRESTは `.select()` を自動でSQLに翻訳してくれるが、

### 無料プランの一時停止と、その対策（2026-08-15）

Supabaseの無料プロジェクトは**1週間ほど使わないと自動で一時停止**する。実際に食らった
（8月頭に触ったきりで停止。データは消えず、ダッシュボードの **Restore project** で数分で戻る）。

放っておくと、**仕様書§1の「気分でないときはパスしてもだいじょうぶ」と噛み合わない。**
7日休んだ人が再開しようとした日に、アプリが動かない状態になる。

対策として [.github/workflows/keep-alive.yml](../.github/workflows/keep-alive.yml) を置いた。
毎日1回、移動カードを1件読むだけの問い合わせを投げる。

- 使うのは `publishable` キー（公開用）。RLSを素通りする `secret` キーは使わない
- そのために `movement_cards` だけ `anon` に `select` を許している（[schema.sql](./schema.sql) §7）。
  カードの文面は CARDS.md として公開済みなので、読めて困る情報ではない
- 必要なGitHubシークレット: `SUPABASE_URL` / `SUPABASE_PUBLISHABLE_KEY`

> **⚠ GitHubの定期実行は、リポジトリを60日間更新しないと自動で止まる。**
> つまり「開発もせず、歩きもしない」期間が2か月続くと、この対策ごと止まる。
> そのときは Actions タブから手で1回動かせば再開する（無効化の通知メールも届く）。

### 認証の状況（2026-08-01時点）

| PC | 状態 |
|---|---|
| **自宅Windows(WSL)** | ✅ SSH鍵あり（2026-05-10作成）・remote設定済み・push確認済み |
| **訓練校Mac** | ⬜ 未設定。`git remote add` と認証手段の用意が要る |

**押さえておくこと。** pushに必要なのは「認証手段」であって、SSH鍵はその一択ではない。

| 認証手段 | 手元に置くもの | 性質 |
|---|---|---|
| SSH鍵 | 秘密鍵ファイル | 無期限・**アカウントの全リポジトリ**に有効 |
| HTTPS + fine-grained PAT | トークン文字列 | 期限付き・**リポジトリを限定できる** |

**訓練校のMacでは PAT を使う。** 自分の管理下にないPCに、無期限・全リポジトリ有効の
秘密鍵を置かないため。トークンなら、もうそのMacに触れなくなっても遠隔で失効できる。

設定: GitHub → Settings → Developer settings → Personal access tokens → Fine-grained tokens
- Repository access: **Only select repositories** → `arquest-app` のみ
- Permissions: **Contents = Read and write**
- Expiration: 訓練の修了日あたり

```bash

git pull    # 既存フォルダで実行。履歴が同一なので衝突しない
```

**pullが成功するまで訓練校側のフォルダは消さないこと。**

訓練校を離れる日: トークンを失効 → Keychainから削除 → ブラウザからサインアウト → 作業フォルダ削除。

### 2台で作業するときの注意

## 8. つまずいたところ（同じ穴に落ちないために）

実際に踏んだもの。コード側にもコメントを残してある。

| つまずき | 直し方 |
|---|---|
| **アプリを開いただけでGPSが動き出し、5時間止まらなかった** | 停止条件を開始条件と同じ密度で設計する（**§4-11。今回いちばん重い**） |
| `create or replace function` で戻り値の名前を変えられない | 先に `drop function` する（schema.sql §5-1） |
| 関数の戻り値の名前がテーブルの列名と同じで「あいまい」エラー | 戻り値を `total_exp` `walked_m` のように別名にする |
| 「やめる」が `permission denied` | 行を消さず、状態を done にして結果を空にする。消す権限が要らなくなった |
| 引き直すとカードが表向きで始まり、どのボタンも押せない | カードのIDを `key` にして部品ごと作り直す |
| 画面ごとに中央がずれる | `scrollbar-gutter: stable`。スクロールバーの有無で幅が変わっていた |
| 景色が途切れる | 並べる絵は「帯の幅 ÷ 絵の幅 + 1」枚。2枚では足りなかった |
| EXIFのGPSを文字列で探して見つからない | 項目は番号（0x8825）で入っている。中身をたどって判定する |
| `useEffect` の中で直接 `setState` できない | ESLintが止める。外部の値は `useSyncExternalStore`、初期化は「IDが一致するか」で表す |
| **跳ねる動きで絵を差し替えると、入れ替わりが見える** | 絵1枚をCSSで潰し伸ばしする。2枚は縦横の比率が違い、輪郭が別物になる |
| **紺地にしたら文字色が場所によって逆転した** | `--ink` と `--ink-card` の2系統に分け、白い面だけ後者を使う（§1.6） |
