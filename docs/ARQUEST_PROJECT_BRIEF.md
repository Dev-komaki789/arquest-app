# アルクエスト（旧称：おつかいクエスト）— プロジェクト仕様書

個人開発ポートフォリオ。職業訓練の成果物。ClaudeDesignでプロトタイプ済み、Figma経由でClaude Codeに引き継いで実装する。

版数：確定版（2枚カード方式）

## 1. コンセプト

**散歩を遊びに。**

- 対象ユーザー（2種類のペルソナ）
  - **きっかけがない人**：運動した方がいいのはわかっているが、外に出る理由がなく動けない
  - **飽きてしまった人**：すでに散歩の習慣はあるが、同じルート・同じ景色に飽きて刺激がない
- 課題：「散歩しよう」では人は動けない。目的がないと外出できない／同じ道はもう飽きた。
- 解決策：曖昧な「移動カード」に従って移動し、着いたら「行動カード」でお題が決まる。行き先も内容も、引くまでわからない。**同じ道を選びようがない**ため、飽きてしまった人にもそのまま効く。
- アプリの役割は「外出のきっかけを作ること」に一本化する（対人的な成長・社交性の獲得は目的にしない）。この役割自体は、ペルソナが広がっても変わらない。
- 自己肯定感や気分が上がることを優先し、達成主義にしすぎない（未達成を咎めない）。
- お金を使うお題も採用するが、いつでも撤退できる設計を前提に、金額の上限はあえて設けない。

## 2. コアメカニクス（確定：移動カード／行動カードの2枚抽選方式）

### 2.1 稼働時間帯と通知
- 利用者は平日／休日それぞれの「動ける時間帯」を事前登録する。
- その時間帯に入ると、Web Pushで通知が届く。
- iPhoneでWeb Pushを受け取るには、利用者がホーム画面に追加（PWAインストール）している必要がある。これは**必須の初回導線**にすること。
- **平日／休日の区分は、移動カードの抽選条件（2.2）にもそのまま使う。** 新しい設定項目を増やさず、既存の稼働時間帯の登録だけで済ませる。

### 2.2 移動カード（出発前に引く）
- 稼働時間になり通知からアプリを開くと、**移動カードを1枚引く**。
- 移動カードの中身は、**特定の座標・エリアに一切紐付かない、曖昧な移動指示**。
- **平日と休日で、移動手段の範囲を変える。**
  - **平日：徒歩のみ。** 例：「30分、適当に歩いて」「行ったことない道を歩いて」
  - **休日：公共交通機関も含む。** 例：「4駅先で降りて」「降りたことないバス停で」
  - 理由：平日は使える時間が短いことが多く、電車・バスを使う指示だと時間内に終わらない・遅い時間に遠方から帰ることになりかねない。休日は時間に余裕があるため、範囲を広げる。
- 徒歩に限らず、（休日は）電車・バスなどの交通機関を使った移動も対象になる。
- **移動カードを引いた時点〜「着いた」と自分で判断するまでの間、位置情報は一切使用しない（追跡しない）。** 行き先の正解は存在せず、利用者の判断だけで進む。

### 2.3 行動カード（到着後に引く）
- 利用者が「着いた」と判断したら、**行動カードを1枚引く**。
- 行動カードも特定の場所には紐づかない汎用的な指示。
  - 例：「用途がわからないものを探そう」「ぱ行のものを見つけよう」「一番いらないものを買う」
- 指示は場所を問わず成立する汎用的な文言だが、実際に何が見つかるかは場所ごとに変わる。
- **行動カードを引いた瞬間から、位置情報の記録（軌跡・距離）が開始される。** これより前の移動区間（電車・バス含む）は記録されない。
- **行動カードのみ、1クエストにつき2回まで再抽選できる。** 移動カードは対象外（行き先からは逃げない）。明らかに実行不可能なお題が出た場合の救済措置。無制限にはしない（簡単なお題だけを選べる抜け道になるのを防ぐため）。
- 再抽選はクライアント側で完結させる（`action_cards`を事前に全件取得しておき、都度サーバーへ問い合わせない）。最終的に選ばれた1件だけをサーバーに記録する。

### 2.4 移動中の表示と、通り道のスポット（任意の補助機能）

移動中の画面が「何も起きない」状態だと虚無になるため、歩いている間にも変化が見えるようにする。**ただし、クエストの行き先を示すものは一切出さない。**

**① 移動中に表示するもの**
- 経過時間・移動距離（`watchPosition`で取得した座標から計算するだけなので、通信は発生しない）
- 相棒が歩くアニメーション（Rive。負荷はほぼゼロ）
- 相棒がときどき喋る一言（「そろそろ半分だね」など。文言の出し分けのみ）

**② 通り道のスポット一覧**
- 画面下部に、歩いている途中の周辺スポットが少しずつ増えていく。
- **クエストの目的地とは完全に無関係。** 「ついでに何か食べる」「気になる店に寄る」ための、純粋な寄り道用の情報。
- **更新は時間ではなく距離で行う。** 前回スポットを取得した地点から**300m以上離れたときだけ**Overpass APIに問い合わせる。立ち止まっている間は問い合わせないので、レート制限・電池消費の問題を回避できる。
- **ただし距離だけを条件にすると、乗り物のときに連射になる（2026-08-15 追記）。** 休日は交通機関のカードが出るため、時速60kmでは300mを18秒で通過してしまう。そこで次の3つをすべて満たしたときだけ問い合わせる。
  - 前回の地点から **300m以上** 離れた（更新すべきかを決めるのは距離）
  - **時速10km未満**（電車・バス・自転車のときは休む。走っている乗り物から寄り道はできないので、探す意味がない）
  - 前回の問い合わせから **60秒以上**（トンネルやビルの谷間でGPSが飛び、速さの計算が乱れたときの保険）
- **探していないときは、その理由を画面に出す。** 黙って止まっていると、壊れているのか判断できないため。
- **検索半径は300m。** 800mだと都市部で結果が上限に達し、「調べ終わった範囲」として記録できないためキャッシュが効かない（[HANDOFF.md](./HANDOFF.md) §4-8）。狭ければ切られず、一度通った範囲は通信ゼロになる。寄り道先を探すのに800m先の店は要らない。
- 取得済みの`pois`から先に表示し、足りない分だけ追加で問い合わせる。来た道を戻る場合は通信ゼロ。

**③ スポットまでのルート表示**
- リストのスポットをタップすると、**そこまでの徒歩ルートを地図に表示する。**
- ルート計算はOSRM（無料）を使用。Leaflet + OpenStreetMapの構成のまま線を引ける（Googleのような「地図を揃えろ」という規約がない）。
- タップしたときだけ1回計算するので、負荷は軽い。
- **これはクエストの行き先へのルートではない。** 行き先そのものが存在しないため、目的地へのルート案内は原理的に出せない。ここで出すのは、あくまで「通りすがりに気になった店」への寄り道の道順。

**④ 設計上の整理（重要）**
- **クエストの行き先のルート → 出さない。** 行き先が存在しないので出せない。「行き先を教えないから寄り道が生まれる」というコンセプトの根幹。
- **通り道のスポットのルート → 出してよい。** クエストと無関係なので、伏せる意味がない。寄り道が「サボり」にならない。
- この機能を使うと**移動中も位置情報が動く**ことになり、2.2の原則（移動中は位置情報を使わない）から外れる。そのため**設定でオン／オフを切り替えられるようにする**。
  - **デフォルトはオフ。** オフの場合は従来どおり、移動中は位置情報を一切使わない。
  - オンにすると、経過時間・距離・通り道のスポット・ルート表示が使えるようになる。
  - 「使わないことを選べる」という誠実さを保ったまま、賑やかな体験も選べるようにする。

### 2.5 達成判定（自己申告）
- 移動カードの「到着」判定はGPSでは行わない。完全に自己申告。
- 行動カードの実行結果も、「できた／まだ・もうすこしねばる」の自己申告制。写真や証拠は必須にしない。
- クエスト完了時に、カメラで写真を撮って日記に記録できる。
- **できなくても、来たこと自体は記録される**（できなかったことを咎めない設計）。

### 2.6 状態の保持（アプリを閉じても進行中のクエストは戻ってくる）
- 移動カードを引いた瞬間に、`quests`テーブルへ即座に記録する（ブラウザのメモリ上だけに置かない）。
- アプリを再度開いたとき、進行中のクエストがあるかを`quests`の状態から確認し、あれば該当する画面（移動中／行動中）にそのまま復帰させる。
- 移動中の区間は位置情報を使っていないため、アプリを閉じている間も追跡の継続は不要。「どのカードを、いつ引いたか」が保存されていれば十分。（2.4の移動中表示をオンにしている場合のみ、移動中も位置情報が動く）
- 行動カードを引いた後（軌跡記録中）も、記録を逐次サーバーに送ることで、アプリを閉じても軌跡が失われないようにする。

### 2.7 軌跡・距離の記録
- 行動カードを引いた瞬間からクエスト完了までの軌跡・距離を記録する。
- 記録は削除せず蓄積し続け、継続の実績として扱う。

### 2.8 地図塗り（方式B：訪れた場所のマスだけを塗る）
- 軌跡をそのまま線として地図に表示すると、GPSのブレでジグザグに見えて読みにくいため、**線ではなくマス目（グリッド）を塗る方式にする**。
- 塗る対象は、**行動カードを引いてからクエスト完了までにいた場所のマスのみ**。通過した経路をなぞって塗るのではなく、到達点を中心に塗る。
- 移動カードの区間（電車・バス含む）はそもそも位置情報を取得していないため、対象にならない。

### 2.9 相棒（キャラクター）
- ホーム画面で相棒「スラりん」が声をかけてくる。達成状況に応じてセリフが変わるが、何もしていない日も否定しない言葉を選ぶ。
- 達成でレベル・EXPが育つ。
- **移動した距離に応じて報酬（おかね）が与えられ、それでアイテムを購入して着せ替えができる。** 距離が報酬に変換される唯一の経路。実装スコープでは最大構成に位置づける。

### 2.10 日記（非公開）
- クエストで見つけたものを、写真＋一言メモで記録する個人的な日記機能。
- **完全に非公開**。共有・いいね・コメント機能は実装しない。
- 写真のEXIF位置情報の削除は将来対応でよい。

### 技術的な注意点（決定事項）
- iOS SafariはWebXR（immersive-ar）に対応していない。カメラ越しのAR経路表示は実現不可のため不採用。
- Googleの各API（Places / Directions / Routes）は「Google以外の地図と組み合わせて使用禁止」という規約があるため不採用。
- **今回の設計では、Overpass API・PostGISは「クエストの成立条件」ではなく、任意の補助機能・軌跡記録のためだけに使う。** 位置情報がなくてもクエスト自体は進行できる設計（2.10参照）。
- **徒歩ルートをOSRM → Valhallaに変更した（実測にもとづく）。** OSRMの公開デモサーバー（router.project-osrm.org）は profile 指定を無視し、`foot` / `walking` / `driving` のどれを指定しても自動車の経路しか返さない。自動車の経路は一方通行・進入禁止の制約を受けるため遠回りになる（実測：阪神尼崎→出屋敷で、徒歩1.34kmに対し1.60km）。OSRMを本番で使うなら自前運用が必要。OSRMはValhalla停止時の代替として実装を残す。詳細は [HANDOFF.md](./HANDOFF.md) §4-1。
- **地図描画をLeaflet → MapLibre GL JSに変更した。** OSMの生タイル（tile.openstreetmap.org）は利用ポリシーでアプリからの利用が強く制限されるため、無料ベースマップ（CARTO）とベクタータイルを使う。MapLibre v6 は Next.js のバンドル後にWeb Workerを見失うという問題があるが、ワーカーを `public/` にコピーして `setWorkerUrl()` で明示することで解決済み（[HANDOFF.md](./HANDOFF.md) §4-3）。
- **Overpassで拾うスポットの範囲は広めに取る。** 2.4のスポット一覧は寄り道のための情報であり、お金を使うお題も採用しているため、飲食店・商店を絞る理由がない。ただし**病院・学校・幼稚園・警察・消防・墓地・斎場は拾わない**（利用者を危険に晒さないため）。

## 7. 地図塗り（方式B）の考え方

グリッドのマス目は、緯度経度を一定間隔で割った番号（`cell_x`, `cell_y`）として管理する。行動カードを引いてからクエスト完了までの`quest_trajectories`のうち、**完了時の位置（`completion_lat/lng`）が属するマスだけ**を`visited_cells`に記録する（すでに記録済みのマスなら`visit_count`を加算するだけ）。

グリッドサイズ（1マスが何mか）は未確定。Figma／実装段階で、地図の見た目とバランスを見ながら決める。

## 10. これまでの重要な議論・却下した案（実装時に蒸し返さないための記録）

- **出前ブロッカー機能**：初期アイデアだが、対象が特定的すぎるため削除済み。
- **AR経路表示**：iOS SafariがWebXRのimmersive-arに対応していないため断念。
- **Googleマップ／Google Places APIでの候補地取得**：無料でない・地図をGoogleに揃える必要がある・キャッシュが30日制限、という理由で不採用。
- **カテゴリ表示（おみせ／しぜん／であい／くらし・ふしぎ 等）**：場所の軸と対人度の軸が混在し曖昧になる問題が解決できず、カテゴリ表示そのものを廃止。
- **対人系のお題**：「このアプリの役割は外に出る理由を作ることであり、社交性を鍛えることではない」という整理のもと不採用。
- **達成記録の共有・いいね機能**：対人プレッシャーや心理的リスクを避けるため不採用。日記は完全非公開。
- **お金を使うお題への金額上限**：撤退できる設計がすでにあるため、上限を設けずに採用。
- **「エリア抽選方式」（地図上にエリアの円を表示し、到着後に1回でどこで×なにをするを抽選する方式）**：一時期これを正式仕様として確定していたが、最終的に不採用。**理由**：この方式では、行き先が実質的に「座標」として決まっており、位置情報の役割が「エリアへの到達判定」という一点に集中しすぎていた。一方で今回採用した2枚カード方式は、移動カードの内容を座標に一切紐付けない曖昧な指示にすることで、「行き先が本当にわからない」という体験を保ちながら、位置情報の利用を「行動カードを引いた後」「検索ボタンを押した時」という必要な場面だけに絞り込める、という点で優れていると判断した。
- **「移動カード後もマップにエリア（円）を表示する」折衷案**：位置情報を使わずに曖昧さを保つ、という2枚カード方式の魅力を薄めてしまうため不採用。
- **軌跡をそのまま線として地図に表示する案**：GPSのブレでジグザグに見えて読みにくいため不採用。マス目を塗る方式（方式B）に統一。
- **継続日数（連続達成日数）の表示**：雨天時など「出かけなくて当然の日」まで実績が途切れる形になり、罰則的に働くため不採用。天気APIとの連携、離脱者への呼び戻し設計もあわせて不要と判断した。

- **クエストの行き先へのルート案内**：移動中にルートを出すと最短経路を歩くだけになり、「行き先を教えないから寄り道が生まれる」というコンセプトが崩れるため不採用。ただし**通り道のスポット（クエストと無関係の寄り道先）へのルートは出してよい**と整理した（2.4参照）。この2つは別物として扱う。
