# アルクエスト（旧称：おつかいクエスト）— プロジェクト仕様書

個人開発ポートフォリオ。職業訓練の成果物。ClaudeDesignでプロトタイプ済み、Figma経由でClaude Codeに引き継いで実装する。

最終更新: 2026-08-03（§1のコンセプト転換と、お題の構造の全面変更を反映）

## 1. コンセプト

**ただ歩くという苦行を、遊びにする。**

- 対象ユーザー：散歩が退屈な人。目的がないと外に出られない人（自分自身がモデル）。
- 課題：「散歩しよう」では人は動けない。歩くこと自体に目的がなく、退屈だから続かない。
- 解決策：アプリが「お告げ」を出す。**どこへ向かうか（移動カード）**と**着いて何をするか（行動カード）**が
  ランダムに決まり、その組み合わせがその日の遊びになる。散歩ではなく"ぼうけん"というフレーミング。
- 遊びのルール：**お金を使わせない／対人ハードルを上げない／できなくても咎めない。**
  「配慮」としてではなく「そういうゲームだから」として設計する。

### 2026-08-03 の方針転換（旧§1からの変更）

当初は「休日、部屋から一歩も出ない人」の**課題解決**として設計していた。
しかし画面・アプリ名・デザイン（クエスト／EXP／相棒／「ぼうけんをはじめる」）は
**最初から遊びの語彙**で作られており、§1だけが課題解決の語彙で取り残されていた。
方針転換というより、**古いまま残っていた部分を実体に合わせる作業**である。

転換によって得たもの：

- 説明が重くならない（「かわいそうな人向け」に聞こえない）。プレゼン・面接で語りやすい
- 対象が広がる（部屋から出ない人 → 散歩が退屈な人）
- 参照先（さんぽ神＝カードゲーム）と語り口が一致する。
  「治療の参考にカードゲームを見る」より「遊びの参考に遊びを見る」ほうが真っ直ぐ
- 「達成主義にしすぎない」との**見かけの矛盾が解消**した。
  ゲームにEXPとレベルがあるのは自然であり、旧§1が古かったために生じていた矛盾だった

**意識して残すこと。** 「気分でないときは、パスしてもだいじょうぶ」「できなくても、来たことは記録されます」
という、やさしさの部分。**遊びは「やらない人」に興味を持たないので、放っておくと薄れる。**
ノルマが無いのが遊びである、という理由づけで残す。

## 2. コアメカニクス

### 2.1 稼働時間帯と通知
- 利用者は平日／休日それぞれの「動ける時間帯」を事前登録する。
- その時間帯に入ると、Web Pushで通知が届く（複数回に分けて通知する想定）。
- iPhoneでWeb Pushを受け取るには、利用者がホーム画面に追加（PWAインストール）している必要がある。これは**必須の初回導線**にすること（iOS SafariはPWAインストールなしではWeb Pushを受け取れない）。

### 2.2 お題の構造 — 移動カード × 行動カード

**参照：ドロッセルマイヤー商會「さんぽ神」**（カードを引き、お告げとして散歩の指示を受け取るカードゲーム）。

お題は**2枚のカードの組み合わせ**で決まる。

| | 例 | 引くタイミング |
|---|---|---|
| **移動カード** | 30分適当に歩いて／行ったことない公園まで歩いて | **出発前** |
| **行動カード** | 用途がわからないものを探そう／ぱ行のものを見つけよう | **到着後** |

前半は「場所」ではなく**行き先の決め方**である。
**行き先が分からないこと自体が面白さの源**なので、目的地を確定させない型もある。

#### 移動カードの類型

| 型 | 例 | 実行可能性の判定 |
|---|---|---|
| **A 時間・距離** | 30分適当に歩いて／1km歩いて | 不要（常に実行可能） |
| **B ランドマーク到達** | 行ったことない公園まで／一番近い神社まで | **必要**（周辺に実在するか） |
| **D 偶然性** | サイコロの目だけ角を曲がる | 不要 |

**B がこのアプリの中心的な価値。**「**行ったことない**公園」は、
カードゲームには原理的に判定できない（プレイヤーの記憶に頼るしかない）。
アプリは `visit_logs` を持っているので**本当に知っている**。ここがアプリである必然性。

**型 C（他人依存・交通機関を伴うもの）は不採用。**
「電車でマークした人と一緒に降りて」のような実例があるが、
判定不能なうえ交通費がかかり、§1の「お金を使わせない」に反する（例外は §2.8 の設定）。

**型 A が常に候補に残るため、「引けるカードが1枚もない」状態は構造的に起きない。**

#### 行動カードは「解釈」を要求する

「散ろう」「痺れよう」のような抽象的な指示は、**何をすれば達成なのかを歩く人が決める。**
その解釈の作業そのものが娯楽であり、**達成の判定は原理的に不可能**。

→ §2.4 の「完全な自己申告制」は不正防止を諦めた妥協ではなく、**この構造から導かれる必然**である。

行動カードは2種類あり、**観察型を主軸**にする。

| 型 | 例 | 場所は効くか |
|---|---|---|
| **観察型（主軸）** | ここで一番古そうなものを見つける／ぱ行のものを探す／聞こえる音を3つ数える | ✅ **どこでも成立するが、答えは場所ごとに違う** |
| 行為型（少量） | 10歩だけ後ろ向きに歩く／深呼吸する | ❌ 場所と無関係。混ぜすぎると「なぜそこまで歩いたのか」が消える |

観察型なら「どこでも成立する」と「その場所ならではの体験」が両立する。
**指示は汎用、答えは場所固有。**

#### 骨格 × 変数で作る

100個を手で書かず、骨格と変数に分けて組み合わせる。

```
〈誰か〉への手土産を見繕おう      誰か: 恩師 / 昔の自分 / 猫 / 宇宙人 …
〈お題〉なものを見つけよう        お題: ぱ行 / 用途がわからない / 一番古そう / 南米っぽい …
〈対象〉を見つけて品評しよう      対象: 階段 / 自販機 / 室外機 / 電柱 …
```

骨格20 × 変数5 で100通りになる。
**固有名詞は必ず変数側に隔離する。** 元ネタには賞味期限があり（芸能人・アニメ・時事）、
知らない人には最初から空振りするため、**古くなったら差し替えられる形**にしておく。

#### ハチャメチャは許容する

無茶な組み合わせは**バグではなく演出**。
相棒が「お告げ」として告げることで、乱数の理不尽さが神秘性に変わる（§2.5）。
**さんぽ神の発明は、乱数を「お告げ」と呼び替えたこと**にある。

止めるのは次の2つだけ。

| | 例 | 判断 |
|---|---|---|
| 面白い破綻 | コンビニで空を見上げる | ✅ **狙い通り**。詩的ですらある |
| **実行不能** | 公園で店員にお礼を言う（店員が存在しない） | ❌ 止める |
| **迷惑・危険** | 病院で大声で笑う | ❌ 止める |

#### このアプリの語彙にしないもの

さんぽ神の実例には次の系統があるが、**対象と目的が違うため採用しない。**

- **攻撃性・自己否定**（行列の人を嘲笑おう／恥をかこう／喧嘩を売ろう／文句をつけよう）
  カードゲームは**人間が読み替える前提**で成立している（嘲笑おう＝心の中で、など）。
  アプリが単独で突きつけると額面通りに受け取られる。§1の「自己肯定感」とも逆を向く。
- **交通機関を伴う移動** — お金がかかる。ただし §2.8 の設定でONにした場合のみ解禁。
- **準備が要るもの**（タイムカプセルを仕込もう／手牌を1個切ろう／他アプリを開こう）
  手ぶらで出た人が実行できない。

#### アプリだからできること

さんぽ神の実例のうち、**カードよりアプリのほうが得意**なもの。実装の狙い目。

- **「2回引き直して、2つを同時進行でこなそう」** — 本当に2枚引ける
- **「アンラッキー！5マス戻ろう」** — 軌跡を持っているので、**本当に戻らせられる**
- **「季節を感じよう」** — 日付・時刻・天気を知っているので、季節や時間帯で出し分けできる

### 2.3 到達判定（二段構え）
1. クライアント側：Geolocation API + Haversine距離計算で「近づいてきたかも」を先行して画面に表示（UX上の即応性のため）。
2. サーバー側：Supabaseの RPC 関数内で PostGIS の `ST_DWithin` を実行し、最終確定する。クライアントの自己申告だけを信用せず、改ざんに強い設計にする。

**到達判定の半径は 100m。**（GPS精度のフィルタ ±50m は「その半分」を根拠にしているので、
片方を変えるときは両方を見直すこと。実装メモ §4-4 参照）

**行動カードの抽選もサーバー側で行う。**
クライアントに任せると、気に入らないお題を無限に引き直せてしまうため。

### 2.4 行動確認（自己申告）
- **すべてのクエストで行動確認を挟む。** 移動カードで到着しただけでは完了せず、
  必ず行動カードのお題があるため。
- 「できた／まだ・もうすこしねばる」の一言確認画面。
- **できなくても訪問自体は記録される**（できなかったことを咎めない設計）。
- 達成の確認は写真や証拠を求めない完全な自己申告制。
  §2.2 のとおり、抽象的なお題は**判定が原理的に不可能**なので、これ以外の選択肢がない。

> **旧仕様からの変更（2026-08-03）**
> 旧：「であい」系のお題だけ行動確認画面を挟み、それ以外は到達判定のみでクリア。
> 新：**全クエストで行動確認**。分岐が消えて1本道になるため、
> `quest_templates.action_type`（`gps_only` / `self_report`）の区別も不要になった。

### 2.5 相棒
- ホーム画面で相棒（プロトタイプでは「ソラ」）が声をかけてくる。
- **相棒は「お告げの語り手」＝ゲームマスター。** 「がんばったね」と励ます役ではなく、
  「きょうの おつげは……」とお題を告げる役。
  この**フレーミングがハチャメチャな乱数を正当化する**（§2.2）ので、機能ではなく構造上の要。
- 達成状況に応じてセリフが変わるが、何もしていない日も否定しない言葉を選ぶ。
- 達成でレベル・EXPが育つ。将来的に着せ替え・図鑑機能を追加予定（優先度は低め）。

### 2.6 地図塗り
- 訪問済みのスポットが地図上で見て分かるようにする（可視化された継続の記録）。
- **実際の地図（MapLibre）の上に、行ったスポットを色づけて残す方式。**
  抽象的なグリッドや「32/96エリア・34%」のような達成率は**採用しない。**
  - 理由1：要件は「行ったスポットが見た目で分かればOK」であり、達成率は目的ではない
  - 理由2：グリッドのセルをどこに記録するかというデータ設計の問題が消える

### 2.7 日記（非公開）
- ミッションで見つけたものを、写真＋一言メモで記録する個人的な日記機能。
- **行動カードの受け皿になる。**「全然映えない写真を撮ろう」「アー写を撮ろう」「川柳を詠もう」
  のような記録型のお題が、そのまま日記に残る。お題と記録が一本の線になる。
- **完全に非公開**。共有・いいね・コメント機能は実装しない（傷つくリスク・ストーカーリスクを構造的に避けるため）。
- 写真のEXIF位置情報の削除は将来対応でよい（非公開機能のため優先度は低い）。

### 2.8 遊ぶ範囲の設定
- 出発前に「どこまで行くか」を決める。**毎回聞かず、設定画面に既定値を持つ**
  （毎回チェック項目を通すと、遊びの入口が重くなる）。
- 項目：**検索半径**（既定値は §6 の `user_settings.search_radius_m`）／**電車移動あり**（既定OFF）。
- 「電車移動あり」は**利用者が自分でONにするopt-in**。
  アプリが勝手に交通費を使わせるわけではないので、§1の「お金を使わせない」と両立する。

### 2.9 遊びの流れ（確定）

```
【設定】どこまで行くか            §2.8（既定値があるので通常は素通り）
   ↓
① 周辺に何があるか調べる          Overpass → pois キャッシュ
   ↓
② 実行可能な移動カードを絞る       ← チェックはここだけ
   ↓
③【抽選1】移動カード              「行ったことない公園まで歩いて」
   ↓
④ 移動（追従・距離の記録）
   ↓
⑤ 到達判定（100m以内 / 30分経過）  クライアント概算＋サーバーPostGIS
   ↓
⑥【抽選2】行動カード              ← ここで初めてお題が判明
   ↓
⑦ できた／まだ（自己申告）
   ↓
⑧ 終了。帰り道は設計しない（下記）
```

**抽選の順序は「チェック → 抽選」。**「抽選 → 実行可能か確認 → 駄目なら引き直し」にすると、
外れるたびに引き直すことになり、郊外ほど遅くなる。
**候補を絞ってから引けば必ず1回で決まる。**

**抽選が2回に分かれる理由。** 出発前に両方引くと、家を出る時点で
「公園に行って、用途がわからないものを探す」と全部わかってしまい、驚きが消える。
到着後に引けば「着くまで何をするか分からない」が保てる。
**伏せているのではなく、まだ存在しない**ので実装も単純。

**帰り道は設計しない（2026-08-03 決定）。**
帰りは疲れ切っている可能性が高く、お題を出すと遊びではなく**義務**になるため。
目的地がそのままゴール。

> 検討したが見送った案：「来た道と違う道で帰ろう」（軌跡データで判定可能）、
> 帰りを日記を書く時間にする、Valhallaで帰路案内を出す。
> 将来、迷子対策の**安全機能**として帰路案内だけ復活させる余地はある（お題ではなく、ただの地図として）。

## 4. デザインシステム

RPGクエスト風。Canvaテンプレートの「空気感」だけを参考にし、素材はオリジナルで再構成（著作権配慮）。

- **色**：スカイブルー `#5B8DEF`（濃色 `#3E6FD8`）、紺 `#1E2A4A`（メッセージウィンドウ背景）、ゴールド `#F5B942`（ごほうび・強調）、グラス `#4CAF7D`（表紙の装飾ストリップ）、カード背景 `#F2F6FF`、強調カード背景 `#FFF3DE`。
- **フォント**：Yu Gothic（游ゴシック）で統一。
- **UIモチーフ**：紺地・白縁のRPGメッセージウィンドウ（相棒のセリフ用）、メニューカード（左上に番号タブ）。
- **色の使い方のルール**：カードの強調色は「新しく追加された・最も差別化になる機能／画面」を示す。デコレーションではなく意味のある強調にする。
- キャラクター（相棒）はCanva素材を使わず、丸・目・ほっぺの単純な図形で構成したオリジナルマスコット。実装時はFigma → Riveで作ったキャラクターに差し替える。

### 技術的な注意点（決定事項）
- **iOS SafariはWebXR（immersive-ar）に対応していない。** カメラ越しのAR経路表示は実現不可。上からのMapLibre地図表示に統一する。
- **Googleの各API（Places / Directions / Routes）は「Google以外の地図と組み合わせて使用禁止」という規約がある。** 今の構成（MapLibre／OSM）を維持する限り、Google系の地理情報APIは採用しない。
- 到達判定は**クライアントの概算（Haversine）＋サーバーの最終確認（PostGIS `ST_DWithin`）**の二段構え。片方だけに頼らない。
- Overpass APIはレート制限のある無料の公共サーバーのため、`pois`テーブルへのキャッシュを必須とする。
- **経路サービスをOSRMからValhallaに変更した。** OSRMの公開デモサーバー（router.project-osrm.org）は profile 指定を無視し、`foot` / `walking` / `driving` のどれを指定しても自動車の経路しか返さない。自動車の経路は一方通行・進入禁止の制約を受けるため遠回りになる（実測：徒歩1.34km に対し1.60km）。OSRMを本番で使うなら自前運用が必要。
- **Overpass APIには User-Agent の指定が必須。** 名乗らないと `overpass-api.de` は406、`kumi.systems` は429で拒否する（OSMの利用規約でアプリの名乗りが求められているため）。また回数制限（429）に実際に到達したため、キャッシュを必須とする判断は実測で裏付けられた。タイムアウト時にも HTTP 200 で `remark` だけを返すことがあるので、`remark` の有無で失敗を判定する。
- **Valhallaは本編では使わない（2026-08-03）。** 行きは「行き先が分からないことが面白さ」なので道順を出すと台無しになり、帰りは §2.9 のとおり設計しないと決めたため。
  実装（[src/lib/routing.ts](../src/lib/routing.ts)）とOSRMとの実測比較は**技術的判断の記録として残す**。捨てるのは実装であって成果ではない。

### 技術力をどこで見せるか（2026-08-03 整理）

「エリアを絞らずランダムにお題を出すだけ」にすると技術の見せ場が消える、という懸念に対する結論。

**行動カードはどこでも成立してよい。技術はそこに置かない。**
位置情報が本質的に必要なのは**移動カード側**であり、技術はそこに集約される。

| 置き場所 | 内容 | ゲームとして必要な理由 |
|---|---|---|
| **移動指示の生成** | 未訪問スポットの空間検索・実行可能性の判定 | 詰みを防ぐ。新鮮さを担保する |
| **到達と距離の判定** | クライアント概算＋サーバーPostGISの二段構え | 「本当に歩いた」の裏付け |

**この2つ以外に技術を足すと「アピールのために付けた」と見透かされる。**

そして最大のアピールは機能の量ではなく、**判断の記録**（[HANDOFF.md](./HANDOFF.md) §4）である。
「動くものを作った」ではなく「**エラーが出ない不具合を実測で見つけ、トレードオフを数字で判断した**」
という記録になっている。これは機能を減らしても一切減らない。

### 6-1. カード関連のテーブル（素案・未確定）

§2.2 の「骨格 × 変数」を実現するための構造。**まだ設計途中。**

```
move_cards（移動カード）
  id uuid PK
  template text            例: 「行ったことない〈対象〉まで歩いて」
  kind text                'distance' | 'landmark' | 'random'
  target_place_type text   kind='landmark' のとき: "leisure=park" など。他はNULL
  requires_unvisited boolean
  duration_min integer     kind='distance' のとき: 30 など。他はNULL

action_cards（行動カード）
  id uuid PK
  template text            例: 「〈お題〉なものを見つけよう」
  kind text                'observe' | 'act'
  variable_set text        使う変数の集合名。変数を含まないカードはNULL

card_variables（変数）
  id uuid PK
  set_name text            例: 'topic', 'someone', 'object'
  value text               例: 'ぱ行の', '用途がわからない'
```

**旧 `quest_templates` は廃止。** 「場所＋行動が1レコード」という前提が §2.2 で崩れたため。
`action_type`（gps_only / self_report）と `social_level`（solo / social）も、
§2.4 で全件が自己申告になり、対人度の概念も消えたので不要。

### 6-2. `pois.category`（4分類）を廃止した理由

旧設計では Overpass のタグ（`shop=bakery` など）を
`explore` / `nature` / `meet` / `errand` の4カテゴリに畳んでから保存していた。

**畳むと情報が失われる。** 移動カードは「行ったことない**公園**まで」のように
**具体的な種類を名指しする**ので、4分類では粒度が足りない。
また4分類は開発者の主観的なマッピングであり、「郵便ポストは用事かたんけんか」という
答えのない悩みを生んでいた。**タグをそのまま持てば、判定が事実ベースになる。**

- 地図のピンの色分けは `place_type` から直接決める（表示の都合であり、お題の分類ではない）
- 日記画面の「であい」「しぜん」ラベルは、**行動カード側**が持つ

**移行の注意：** 現在 `pois` に約120件あるが、`place_type` を持っていない。
**件数が少ないうちに消して取り直すのが安い**（Overpassには回数制限がある）。

### 6-3. Overpass の取得対象を広げてよくなった

旧 [overpass.ts](../src/lib/overpass.ts) は「お金を使わせない」「対人ハードルを上げない」を
**場所の選定で守ろうとして**いた（飲食店を広く拾わない、店員と話す場所を隔離する等）。

§2.2 で**場所は行き先の口実に過ぎず、お金も対人も行動カードが決める**と整理されたため、
場所を絞る理由がなくなった。むしろ**ピンは多いほうがよい**（移動カード型Bの候補が増える）。

これは次の2つを同時に解消する。
- 候補の枯渇（訪問済みを除外し続けるといつかゼロになる問題）
- カテゴリの偏り（尼崎・梅田で取得した120件は errand 64 / explore 29 / meet 24 / **nature 3**。
  都市部では「しぜん」が出せなかった。→ しぜんは**場所ではなく行動側**にあるので問題ごと消滅）

## 7. RPC関数の設計

§2.9 の流れに対応して、2つに分かれる。

```sql
-- ① 出発前：実行可能な移動カードを絞って抽選する
draw_move_quest(p_user_id uuid, p_lat, p_lng, p_radius_m)
  ① 周辺の pois を空間検索（ST_DWithin）
  ② visit_logs と突き合わせて未訪問を判定
  ③ 実行可能な move_cards だけに絞る
     - kind='distance' は常に可能
     - kind='landmark' は target_place_type のスポットが（未訪問で）実在するときだけ
  ④ 抽選し、quests に記録して返す

-- ② 到着時：到達を確認し、行動カードを抽選する
complete_arrival(p_quest_id uuid, p_lat, p_lng)
  ① ST_DWithin で到達を確認（§2.3のサーバー側最終確認）
  ② 合格なら action_cards から抽選し、変数を埋めて quest_text を確定
  ③ quests.arrived_at と visit_logs を記録して返す
```

**抽選をサーバー側で行うこと。** クライアントに任せると気に入らないお題を無限に引き直せてしまう。
§2.3 の「クライアントの自己申告だけを信用しない」は、到達判定だけでなく抽選にも及ぶ。

参考（旧 `complete_quest` の雛形。到達判定の書き方として有効）:

```sql
create extension if not exists postgis;

v_ok := ST_DWithin(
  v_target,
  ST_MakePoint(p_lng, p_lat)::geography,
  v_radius
);
```

## 8. 実装の推奨順序（MVPへの積み上げ）

1. 現在地を取得して画面に表示するだけ（Geolocation API） … ✅
2. 地図を表示し、現在地マーカーを置く（MapLibre GL JS） … ✅
3. Overpass APIで周辺スポットを取得し、ピンを置く … ✅
4. 取得したスポットをSupabaseの `pois` にキャッシュする … ✅
5. ~~OSRMでルートを取得し、地図に線を描く~~ … ✅（実装済みだが §5 のとおり本編では使わない）
6. `watchPosition` で現在地を継続取得し、マーカーを追従させる … ✅
7. Haversineで現在地・目的地間の距離を計算する … ✅
8. SupabaseでPostGISを有効化し、到達判定のRPCを作る … ⬜ **次はここから**
9. 到達したと思われたタイミングでRPCを呼び、サーバー側で最終確認する … ⬜
10. 到着後に行動カードを抽選し、行動確認画面を出す … ⬜

> **⑧の前提について（重要）**
> ⑧の `complete_arrival` は `quests` テーブルを必要とし、`quests` は `users` を参照する。
> この順序は**ログイン機能（画面1）と `users` テーブルを飛ばしている。**
> そのまま着手すると、先に作るものが芋づる式に出てくる。
>
> **推奨：まず「スポットIDと半径」だけでPostGISの到達判定を動かし、動くと分かってから
> `quests` を被せる。** ①〜⑦と④がこの進め方で成功している。

## 11. これまでの重要な議論・却下した案（実装時に蒸し返さないための記録）

- **出前ブロッカー機能**：初期アイデアだが、対象が特定的すぎるため削除済み。
- **AR経路表示（カメラ越しに矢印を表示する演出）**：iOS SafariがWebXRのimmersive-arに対応していないため断念。上からの地図表示のみを採用。
- **Googleマップ／Google Places APIでの候補地取得**：無料でない・地図をGoogleに揃える必要がある・キャッシュが30日制限、という3つの理由で不採用。Overpass APIを継続使用。
- **達成記録の共有・いいね機能**：対人プレッシャーや心理的リスクを避けるため不採用。日記は完全非公開。
- **ミッションを目的地に着くまで完全に非公開にする案**：一人用アプリとしては不安要素になりうるとして中間案に着地していたが、
  **2026-08-03 の構造変更で自然に解決した。**「伏せる」のではなく、行動カードは到着するまで**まだ存在しない**（§2.9）。
- **「場所 × 行動」でお題を作る案**（2026-08-03 の途中案）：
  実際のプレイを見ると、前半のカードは場所ではなく**移動のしかた**だった。「移動 × 行動」に修正。
- **場所のカテゴリ（4分類）でお題を選ぶ案**：§6-2 のとおり、畳むと情報が失われるため廃止。
  「近くに店があるか」は分類ではなく**OSMのタグで事実として判定する**。
- **行動ごとの「必要条件」テーブル**：どこでも成立する行動だけにしたので不要になった。
  「食べたことないものを食べよう」のような飲食・購買を伴うお題を作らないことで、
  営業時間の考慮も不要になった（夜は店が閉まっている問題）。
- **帰り道にもお題を出す案**：§2.9 のとおり見送り。疲れているときの課題は義務になる。
- **地図塗りの抽象グリッド（32/96エリア・34%）**：§2.6 のとおり実地図方式に変更。
- **対人度★（1〜5 または 1〜3）と「静かなモード」**：
  §2.2 で対人を伴う行動そのものを作らないと決めたため、概念ごと不要になった。
